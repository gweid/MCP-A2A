# MCP-RAG 项目说明

## 1. 项目定位

这是一个使用 TypeScript 实现的最小化 MCP + RAG 命令行示例项目。

项目将“文档向量化与语义检索”封装为独立的 MCP Server，再由 MCP Client 固定执行“先检索、后调用大模型回答”的 RAG 流程。

当前示例场景是中文医学知识问答，主要用于教学和验证 MCP/RAG 的完整链路，不适合作为生产级知识库或真实医疗系统使用。

## 2. 核心工作流程

```text
启动 Client
  │
  ├─ 自动启动 MCP Server（stdio 子进程）
  │
  ├─ 将内置医学文档发送给 index_docs
  │     ├─ 调用 Embedding API
  │     └─ 将向量存入内存索引
  │
  └─ 用户输入问题
        ├─ 调用 retrieve_docs
        ├─ 对问题生成向量
        ├─ 检索 Top-K 相关文档
        ├─ 将文档和问题组合成 Prompt
        └─ 调用聊天模型生成最终回答
```

主要调用链：

- 启动和索引：`src/client.ts:44-58`
- 用户问答编排：`src/client.ts:60-101`
- MCP 检索工具：`src/server.ts:46-96`
- 内存向量搜索：`src/vector-store.ts:43-58`

本项目不是由模型自主决定是否调用工具。Client 会固定先调用 MCP 检索，再调用 LLM，属于明确编排的 RAG Pipeline。

## 4. 主要模块

### 4.1 `src/client.ts`

应用入口和流程编排层，负责：

- 加载环境变量。
- 定义内置的中文医学示例文档。
- 自动启动 MCP Server 子进程。
- 连接 MCP Server 并检查必需工具。
- 调用 `index_docs` 建立文档索引。
- 读取用户在终端中输入的问题。
- 调用 `retrieve_docs` 获取相关文档。
- 将检索结果和用户问题提交给聊天模型。
- 输出检索内容和最终答案。
- 在退出或发生异常时关闭相关资源。

### 4.2 `src/server.ts`

MCP Server，负责创建 Embedding 客户端、维护向量索引并暴露以下工具：

#### `index_docs`

接收文档列表，调用 Embedding API 生成向量，并将文档及其向量写入内存索引。

#### `retrieve_docs`

接收用户问题和 `top_k` 参数，对问题生成向量，然后从内存索引中检索最相关的文档。

Server 通过 stdio 与 Client 通信。

### 4.3 `src/vector-store.ts`

独立的内存向量存储模块，负责：

- 保存文档及其向量。
- 校验向量维度和数值合法性。
- 使用平方 L2 距离进行全量相似度计算。
- 按距离从小到大排序。
- 返回 Top-K 文档、索引和距离。

该模块不依赖 MCP SDK 或模型 SDK，是项目中相对独立的检索核心。

### 4.4 `test/`

项目包含两类测试：

- `test/vector-store.test.ts`：验证向量距离排序、空索引、`topK` 边界、错误维度和非法数值等行为。
- `test/mcp-server.test.ts`：验证 MCP Server 可以通过 stdio 启动，并暴露 `index_docs` 和 `retrieve_docs` 工具。

## 9. 当前限制

项目目前没有实现：

- 文件上传和文档解析。
- 自动文档分块。
- 持久化向量数据库。
- 文档 ID、标题、来源、页码等 metadata。
- 文档更新、删除和去重。
- 相关性阈值。
- 检索结果重排。
- 可信引用和来源追踪。
- 多用户、权限和审计能力。
- API 超时、重试、限流和缓存。
- 模型自主决定是否调用工具。
- 完整的医学安全和低置信度拒答机制。

向量数据只保存在 MCP Server 进程内存中。Server 退出后索引会消失，Client 下次启动时会重新调用 Embedding API 建立索引。

当前检索实现会遍历和排序全部向量，适合小规模演示，不适合大型文档库。

## 11. MCP 通信生命周期

按照 MCP 规范，当前项目中的 MCP 连接生命周期可以分为三个主要阶段：

1. 初始化阶段（Initialization）
2. 运行阶段（Operation）
3. 终止阶段（Shutdown）

需要注意，创建 Server 子进程和建立 stdio Transport 是初始化握手的前置条件；聊天模型 API 和 Embedding API 的调用则是项目业务实现的一部分，不属于 Client 与 MCP Server 之间的协议通信。

### 11.1 整体时序

```text
Client                         MCP Server
  │                                │
  │  创建并启动 stdio 子进程        │
  │───────────────────────────────>│
  │                                │
  │       初始化阶段                │
  │  initialize request            │
  │───────────────────────────────>│
  │  initialize response           │
  │<───────────────────────────────│
  │  notifications/initialized     │
  │───────────────────────────────>│
  │                                │
  │       运行阶段                  │
  │  tools/list request            │
  │───────────────────────────────>│
  │  tools/list response           │
  │<───────────────────────────────│
  │                                │
  │  tools/call: index_docs        │
  │───────────────────────────────>│
  │  tools/call response           │
  │<───────────────────────────────│
  │                                │
  │  tools/call: retrieve_docs     │
  │───────────────────────────────>│
  │  tools/call response           │
  │<───────────────────────────────│
  │                                │
  │       终止阶段                  │
  │  关闭 MCP/stdio Transport       │
  │───────────────────────────────>│
  │       Server 进程退出           │
  │                                │
```

### 11.2 Transport 建立

Client 首先创建 `StdioClientTransport`：

```ts
const transport = createServerTransport();
```

相关实现位于 `src/client.ts:37` 和 `src/client.ts:111-122`。

该 Transport 会使用当前 Node.js 进程启动 `src/server.ts` 子进程，并建立以下通信通道：

- Client 向 Server 的标准输入 `stdin` 写入 MCP 消息。
- Server 通过标准输出 `stdout` 向 Client 返回 MCP 消息。
- Server 的日志可以通过标准错误 `stderr` 输出，不进入 MCP 消息通道。

Server 端通过以下代码连接 stdio Transport：

```ts
await server.connect(new StdioServerTransport());
```

位置：`src/server.ts:98`。

建立 stdio 通道本身属于传输层准备工作。通道建立以后，双方才会进行 MCP 初始化握手。

### 11.3 初始化阶段（Initialization）

Client 通过以下调用建立 MCP 连接：

```ts
await mcp.connect(transport);
```

位置：`src/client.ts:45`。

虽然源码中没有直接写出 `initialize` 消息，但 MCP SDK 会在 `connect()` 内部完成标准初始化序列：

```text
Client -> Server：initialize request
Server -> Client：initialize response
Client -> Server：notifications/initialized
```

#### `initialize request`

Client 向 Server 提供：

- Client 支持或期望使用的 MCP 协议版本。
- Client 的能力集合。
- Client 的实现信息，例如名称和版本。

当前 Client 的实现信息来自：

```ts
const mcp = new Client({
  name: "mcp-rag-client",
  version: "0.1.0",
});
```

位置：`src/client.ts:38-41`。

#### `initialize response`

Server 返回：

- 最终采用的 MCP 协议版本。
- Server 支持的能力集合。
- Server 的实现信息。

当前 Server 的实现信息来自：

```ts
const server = new McpServer({
  name: "mcp-rag",
  version: "0.1.0",
});
```

位置：`src/server.ts:30-33`。

Server 注册了 `index_docs` 和 `retrieve_docs`，因此向 Client 提供了工具能力。工具注册位置分别为 `src/server.ts:46-67` 和 `src/server.ts:69-96`。

#### `notifications/initialized`

Client 收到并接受初始化响应后，会发送 `notifications/initialized` 通知，表示初始化阶段结束，可以开始正常协议操作。

通知与请求的区别是：通知不要求对方返回响应。

因此，初始化阶段不应描述为“客户端单向请求服务器的功能支持”，更准确的说法是：

> Client 与 Server 交换实现信息，并协商协议版本和双方能力；协商成功后，Client 发送 `notifications/initialized` 通知，宣告正常运行阶段开始。

### 11.4 运行阶段（Operation）

初始化完成后，双方通过 JSON-RPC 2.0 消息交换 MCP 请求、响应和通知。

当前项目主要使用工具发现和工具调用能力。

#### 获取工具列表

Client 执行：

```ts
const listedTools = await mcp.listTools();
```

位置：`src/client.ts:47`。

协议层面对应：

```text
tools/list request
tools/list response
```

Client 随后检查 Server 是否包含必需的 `index_docs` 和 `retrieve_docs` 工具，见 `src/client.ts:47-50` 和 `src/client.ts:149-155`。

#### 调用 `index_docs`

Client 执行：

```ts
const indexResult = await mcp.callTool({
  name: "index_docs",
  arguments: { docs: medicalDocuments },
});
```

位置：`src/client.ts:53-57`。

协议层面对应一次 `tools/call` 请求。Server 收到请求后执行 `index_docs` 处理函数：

1. 调用 Embedding API 为文档生成向量。
2. 将文档和向量写入内存向量索引。
3. 返回包含索引结果的 `tools/call` 响应。

Server 端实现位于 `src/server.ts:46-67`。

#### 调用 `retrieve_docs`

Client 执行：

```ts
const retrievalResult = await mcp.callTool({
  name: "retrieve_docs",
  arguments: { query: question, top_k: 3 },
});
```

位置：`src/client.ts:73-77`。

Server 收到请求后：

1. 为查询文本生成 Embedding。
2. 在内存向量索引中进行 Top-K 检索。
3. 将相关文档作为工具结果返回 Client。

Server 端实现位于 `src/server.ts:69-96`。

#### 当前项目中的通知

MCP 运行阶段允许双方发送通知，但当前项目没有显式定义业务级 MCP 通知。项目中最明确的通知是初始化阶段由 SDK 自动发送的 `notifications/initialized`。

因此，将运行阶段表述为“交换请求和通知”在协议层面是正确的，但结合当前实现，更精确的说法是：

> 当前项目在运行阶段主要交换 `tools/list` 和 `tools/call` 请求及其响应，暂未显式使用业务级通知。

### 11.5 MCP 与外部模型 API 的边界

以下聊天模型调用不属于 MCP 通信：

```ts
await LLM.chat.completions.create(...);
```

位置：`src/client.ts:80-93`。

它发生在 Client 已经通过 MCP 获得检索结果以后，属于 Client 对外部聊天模型服务发起的普通 API 请求。

Server 内部的以下 Embedding 调用同样不是 MCP 协议消息：

```ts
await embeddingClient.embeddings.create(...);
```

位置：`src/server.ts:35-43`。

它是 MCP 工具处理函数内部的实现细节。完整边界如下：

```text
Client --MCP/stdio--> MCP Server --HTTP API--> Embedding 服务

Client --HTTP API--> 聊天模型服务
```

因此，MCP 负责的是 Client 与检索 Server 之间的工具发现和调用，不直接规定 Server 如何生成向量，也不负责 Client 最终调用哪个聊天模型。

### 11.6 终止阶段（Shutdown）

用户输入“退出”时，Client 跳出交互循环：

```ts
if (question === "退出") {
  break;
}
```

位置：`src/client.ts:65-67`。

无论程序正常退出还是发生异常，`finally` 都会执行资源清理：

```ts
} finally {
  terminal.close();
  await mcp.close();
}
```

位置：`src/client.ts:103-106`。

其中：

- `terminal.close()` 关闭命令行输入接口。
- `mcp.close()` 关闭 MCP Client 和底层 stdio Transport。
- stdio Transport 关闭后，由 Transport 管理的 MCP Server 子进程随之结束。
- Server 进程中的内存向量索引随进程退出而释放。

MCP 没有像部分其他协议那样要求先发送一个标准 `shutdown` 请求，再发送 `exit` 通知。对于当前 stdio Transport，终止主要通过关闭连接和子进程完成，而不是调用某个业务工具或交换自定义关闭消息。

因此，终止阶段更准确的表述是：

> 用户退出或程序发生异常时，Client 调用 `mcp.close()` 关闭 MCP 连接及底层 stdio Transport，由 Transport 管理 Server 子进程的结束，同时释放终端接口和 Server 内存资源。

### 11.7 三阶段准确表述

对于当前项目，推荐使用以下描述：

> 整个 MCP 连接生命周期分为三个阶段：
>
> 1. **初始化阶段**：Client 建立 stdio Transport，并通过 `initialize` 请求与 Server 协商协议版本、能力集合和实现信息；Server 响应后，Client 发送 `notifications/initialized` 通知，表示初始化完成。
> 2. **运行阶段**：Client 与 Server 通过 JSON-RPC 2.0 交换请求、响应和通知。当前项目通过 `tools/list` 获取工具列表，并通过 `tools/call` 调用 `index_docs` 和 `retrieve_docs` 工具。
> 3. **终止阶段**：用户退出或程序发生异常时，Client 调用 `mcp.close()` 关闭 Transport 和 Server 子进程，并释放终端、连接和内存索引等资源。MCP 本身没有要求发送单独的标准 `shutdown` 请求。

## 12. 总结

本项目可以概括为：

> 一个展示如何使用 MCP 将向量检索能力工具化，并由 TypeScript Client 编排完成 RAG 问答的最小示例。

它适合用于学习：

- MCP Client 和 Server 如何通过 stdio 通信。
- 如何定义、发现和调用 MCP Tools。
- 如何将 Embedding、向量检索和聊天模型串联成 RAG 流程。
- 如何分离问答编排、协议工具和向量检索逻辑。

如果要进一步产品化，应优先补充持久化文档索引、文档导入与分块、metadata、相关性控制、API Mock 测试、异常恢复和安全治理能力。
